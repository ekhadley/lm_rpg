# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

LM RPG is an LLM-powered text RPG engine. A Flask/SocketIO backend streams LLM responses (via OpenRouter) to a vanilla JS frontend. The LLM acts as game master, using tool calls (dice rolls, story-context read/write) to manage game state. Multiple game systems (Harry Potter, D&D 5e, The Walking Dead) are pluggable. The app has two modes, switched by a toggle above the sidebar: **Play** (the chat) and **Studio** (regenerate one captured turn under two arms — each an arbitrary model + instruction version — side by side).

**Story context** (the PC sheet, story plan, summary, NPC sheets) is *not stored as files on disk*. It lives in an in-memory `dict[str, str]` (`narrator.files`) that is the single source of truth for the in-progress turn, and is reconstructed from the history tree on every navigation. The model's file tools (`read_file`/`write_file`/etc.) are just dict operations on this. Entry names are **extensionless** (`pc`, `story_plan`, `story_summary`, `firstname_lastname` for NPCs) — the model never sees a `.md` extension. Only the shared instruction files in `instructions/` are real files on disk, live-read into the system prompt.

## Running

```bash
# From project root, with .venv activated:
python app.py
# Runs on http://localhost:5001
```

Requires `OPENROUTER_API_KEY` in `.env`. Set `DEBUG=1` for verbose logging.

**The user runs the server, not Claude.** Never start, kill, or restart it while implementing — the user keeps it running and controls its lifecycle. If running it is genuinely necessary to make progress, say so and let them do it. Verify changes instead by importing modules or exercising backend functions directly against on-disk data (e.g. `python -c` against `studio.listRuns` or a story's `history.json`); for frontend changes, describe what changed and ask them to look.

## Project Structure

**Backend flow:** `app.py` (Flask+SocketIO routes) → `narrator.py` (orchestration, system prompt assembly, history tree) → `openrouter.py` (SSE streaming, tool call loop) → `model_tools.py` (tool execution). `studio.py` is a second, parallel consumer of `openrouter.py` that bypasses the narrator entirely.

- **app.py** — Server entry point. SocketIO event handlers for story CRUD (create, copy, delete), user messages, retry, edit, branch switching, archive, forking (`fork_story`), manual story-context edits (`save_story_file`/`create_story_file` → `narrator.editFile`, `delete_story_file` → `narrator.deleteFile`), cache-mode setting (a global `settings` dict), and the studio events (`capture_eval_turn`, `list_eval_turns`, `delete_eval_turn`, `studio_run`, `list_studio_runs`, `load_studio_run`, `get_studio_options`). Global `narrator` object holds active state. Serves stories at `/stories/<name>` for direct linking.
- **narrator.py** — Owns the `TurnTree` (branching conversation history; see `history.py`) and `self.files`, the in-memory story-context dict (mutated in place during a turn; reset from the tree on every navigation via `_setFiles`). Loads story context (plan, PC, summary) into system prompt via XML tags. Rebuilds the provider's flat message list as `[system] + active branch` on each turn. Looks up the system's toolbox factory in `model_tools.SYSTEM_TOOLBOXES`, passing it `self.files`. Transforms messages between OpenRouter and frontend formats. Branch ops: `regenerate_turn` (retry → new sibling), `edit_turn` (edit → new branch from grandparent), `switch_branch` (navigate siblings). `editFile`/`deleteFile` persist a manual story-context change via `_commitFiles`, which folds the whole context into the current leaf's `files` delta (seeding a hidden synthetic root if the story has no turns yet). `fork_to(node_id, name, root)` writes a fresh story whose history is the linear path root→node (story context rides along in the copied deltas, source untouched); `root` is `EVAL_STORIES_DIR` when the studio captures a turn. Thinking effort set to "max".
- **history.py** — `TurnTree`: a branching tree of turns. Each node is one user message OR one narrator response (the assistant/tool messages from a single tool-calling loop); nodes alternate role down a path. The active path is reconstructed by walking `parent` links up from `current_leaf`. The system message is never stored — it's prepended live when building model context. Each node also carries a `files` **delta** (changed story-context entries that turn; `None` value = tombstone for a deleted entry); `file_state_at(node)` replays deltas root→node to reconstruct full story-context state. This makes the tree the authoritative store for story content and enables rollback. Handles serialize/deserialize and `migrate_from_flat` for legacy flat-list histories.
- **openrouter.py** — `OpenRouterProvider` holds the flat message list (rebuilt by the narrator from the active branch) and streams responses. Supports prompt caching via `cache_mode` ("none" | "5m" | "1h") with a moving cache breakpoint (`_with_cache_anchor`). `OpenRouterStream` parses SSE with retry logic. Handles reasoning/thinking output (both `delta.reasoning` and `delta.reasoning_details` formats) and multi-turn tool calling loops. Tracks per-message usage/cost data via `getCostStats()`.
- **model_tools.py** — Tool definitions are plain functions with structured docstrings that get auto-parsed into OpenAI function schemas. `Toolbox` class manages registration, schema generation, and execution. Args with a default value in the function signature are optional in the schema; the rest are required. `BASE_HANDLERS` (file tools) are shared by every system; each system factory adds its own dice tool. `SYSTEM_TOOLBOXES` maps each system name to a factory; a factory takes the narrator's `files` dict and threads it into every handler as a default kwarg. File tools (`list_files`, `read_file`, `write_file`, `append_file`) are pure dict operations on that in-memory story-context dict — no disk I/O. Entry names are extensionless (the model is never shown or asked for a `.md`). Dice tools: `roll_dice` (string `XdY`, used by `hp`/`twd`) and `dnd_dice` (structured `sides`/`count`/`multiplier`/`bonus`/`advantage`/`disadvantage`/`desc`, used by `dnd5e`).
- **callbacks.py** — `WebCallbackHandler` emits SocketIO events for streaming text, thinking, and tool calls to the frontend. Tracks output state transitions. `StudioCallbackHandler` is the studio's equivalent: same events tagged with `run_id`/`lane` so the frontend routes each chunk to its column, and it trips the caching gate on the first output of a primer lane.
- **studio.py** — The A/B studio. A captured turn lives in `eval_stories/<id>/` with the exact on-disk shape of a story (`info.json` + `history.json`) — it is a fork of the source story trimmed to that turn, so its state is frozen and the source is untouched. `runStudio` reads the turn's frozen context (`_turnContext`: messages up to and including the user message being answered, plus story context at that point) and starts `n` background lanes per **arm**, an arm being `{"model": str, "version": int}` — so the two sides can differ in model, in prompt version, or in both. Each lane (`_runLane`) builds its own `OpenRouterProvider` on that arm's model, over its own copy of the story context, with the system prompt pinned via `getFullStoryInstruction(..., versions={base: arm["version"]})` — so a studio run never touches the live narrator or any story tree. Lane ids are `{side}-{i}` with side in `ab`, since two arms may share a version. When all lanes finish, the run is saved to `eval_stories/<id>/runs/<timestamp>.json`; `listRuns`/`loadRun` back the past-run dropdown, `_replayEvents` flattening saved provider messages into the same ordered event stream a live run emits.
- **utils.py** — Story/system directory management, history archival (current → `previous/{n}.json`), story copying, colored logging. `resolveInstructionFile(base, version=None)` maps an instruction base name to its on-disk file: an explicit `{base}{version}.md` if a version is given, else `{base}.md` if present, else the highest-numbered `{base}{n}.md` (used by prompt assembly, app.py's rulebook viewer, and the studio); `listInstructionVersions(base)` enumerates the available numbers for the studio's version pickers. `getFullStoryInstruction(system_name, files, versions=None)` assembles the system prompt from the resolved instruction files plus the in-memory story-context entries; `versions` pins a base to an exact version (`{"core": 0}`), which is how each studio arm gets its own prompt. `copyStory(source, name, model, mode)` takes one of two modes: `"duplicate"` copies `history.json` + `previous/` verbatim (the story context rides along inside the tree), while `"run"` reads the source's **setup** — its story context at the active path's root, i.e. before the first turn (`_sourceFileState(at_start=True)`) — and seeds a fresh tree whose hidden root carries it, giving a story with that context and no messages. A `"run"` copy returns `None` when the setup is empty, which is the case for any story whose context was first written *during* turn 1 rather than seeded beforehand.

**Frontend** (no build step, vanilla JS with ES6 modules):
- `frontend/templates/index.html` — Single-page app: left sidebar (Play/Studio mode toggle over the story list or captured-turn list), chat area, studio area, right sidebar (story context + system instructions)
- `frontend/static/main.js` — Entry point, imports and initializes all modules
- `frontend/static/state.js` — Centralized state, DOM references, socket connection
- `frontend/static/chat.js` — SocketIO message handlers, Markdown rendering (Marked.js), history rendering, `initChat()` wires all socket events
- `frontend/static/reasoningRow.js` — Reasoning row system: collapsible dropdown rows holding the model's reasoning chunks, tool calls, and dice rolls in the order they occurred; assistant turn wrapper management
- `frontend/static/messageActions.js` — Retry and edit-message UI (confirmation popups, DOM manipulation, history truncation)
- `frontend/static/debugViewer.js` — Debug conversation viewer modal (`exportConversation`, message rendering with expandable rows)
- `frontend/static/story.js` — Story list CRUD, context menu (**Duplicate** and **New Run** are two presets over the same copy modal — `COPY_MODES` supplies each one's title, icon, button label, name suffix and one-line description, and the mode is the only thing sent to the server), story-context list (inline "+" row to create an entry, hover trash to delete) and viewer with collapsible TOC and a Raw mode (editable textarea; Save writes back via `save_story_file`), right sidebar resize
- `frontend/static/ui.js` — Popups (hover + pinnable), cost display, archive/confirm dialogs, error notice (`showErrorPopup`, wired to the server's `error` event in `chat.js`), theme system
- `frontend/static/studio.js` — Studio mode: the Play/Studio toggle (`setMode` swaps sidebar list and main area), captured-turn list, run controls (instruction base, a model + version per arm, n, cache), and the lane columns — one per arm, `n` lanes each, each streaming its own reasoning/narration/tool events live and replayable from a past run
- `frontend/static/dropdowns.js` — Custom dropdown component with keyboard navigation
- `frontend/static/styles.css` — 7 themes (Discord, Gruvbox Dark, Leather & Gilt, Tavern, Parchment, Study, Green Lamp) via CSS variables. Book-style narration (EB Garamond font).

**Game systems**:
- `instructions/core*.md` — Shared GM instructions loaded for every system.
- `instructions/{name}*.md` — Per-system ruleset (presence is what makes a system valid).
- Instruction files can be versioned: `resolveInstructionFile` loads `{base}.md` if it exists, otherwise the highest-numbered `{base}{n}.md` (e.g. `core1.md`/`core2.md` → `core2.md`). Lower-numbered versions are kept so the studio can run them head to head.
- Toolbox factory for the system lives in `model_tools.SYSTEM_TOOLBOXES`. Currently registered: `hp`, `dnd5e`, `twd` (all share `BASE_HANDLERS` plus a dice tool). An instruction file with no registered toolbox (e.g. `got.md`) is not an active system.
- Files prefixed with `_` in `instructions/` (e.g. `_story_planning_context.md`, `_hp.md`, `_core.md`) are archived/reference material, not loaded by code.

**Stories** (`stories/{name}/`): Each is a self-contained directory with `info.json`, `history.json`, and an optional `previous/` folder for archived conversations. Story content (PC, plan, summary, NPC sheets) is **not** stored as files here — it rides inside `history.json` as per-turn deltas in the tree. (Pre-refactor story dirs may still contain stray `pc.md` / `story_plan.md` etc.; these are no longer read and are simply ignored — no migration is done.)

**Captured turns** (`eval_stories/{id}/`): The studio's corpus. Same shape as a story (`info.json`, `history.json`) plus a `runs/` folder of saved studio runs. Both `stories/` and `eval_stories/` are gitignored — they're local data.

## Key Patterns

- **Tool definitions** use docstring parsing, not decorators: first line is `tool_name: Description`, subsequent lines are `param_name (type): Description`. The function signature + docstring is the schema.
- **Message flow**: User input → SocketIO → narrator → OpenRouter stream → callbacks emit SocketIO events → frontend renders incrementally.
- **System prompt** is assembled from the resolved core + system instruction files (real files on disk) + optional story-context entries pulled from the in-memory `files` dict (`story_plan`, `pc`, `story_summary`), each wrapped in XML tags (`<core_instructions>`, `<system_instructions>`, `<story_plan>`, `<player_character>`, `<story_summary>`). System prompt is refreshed on history load (live version, not frozen).
- **Story context is tree-authoritative** (`narrator.files`): a single in-memory `dict[str, str]` mutated in place by the file tools during a turn, then diffed against the parent state to store a `files` delta on the new tree node. On any navigation (load, branch-switch, rollback, retry/edit baseline) it is reset to `file_state_at(target)`. The user can also hand-edit an entry in the file viewer's Raw mode, or create/delete entries from the Story Context sidebar; all of these fold into the *current leaf's* delta, so a manual change is local to the active branch — switching to a sibling branch or rolling back past that turn reverts it. `utils.PROMPT_CONTEXT_FILES` names the three entries the system prompt pulls in by name (`story_plan`, `pc`, `story_summary`); the new-entry row flags them as you type since creating one has a much bigger effect than any other name. No story content is read from or written to disk — `history.json` is the only persistent copy. Names are extensionless; the model never sees `.md`. A crash mid-turn loses the in-progress edits (history.json is only written at end-of-turn) — accepted, and cleaner than partial disk writes.
- **Reasoning rows**: Each assistant turn renders as an ordered stack of collapsible reasoning rows (reasoning chunks + tool calls + dice, in the sequence the model produced them) interleaved with narration blocks. A row shows a "Reasoning" label + gears icon, a `…` animation while reasoning is ongoing, and expands on click. Tool calls use orange styling to stand apart from reasoning text.
- **Branching history (`TurnTree`)**: History is a tree, not a flat list. Retrying a turn adds a new sibling branch; editing a user message branches from the grandparent; the frontend can switch between sibling branches. Only the active path (root → `current_leaf`) is sent to the model. Persisted as a serialized tree in `history.json`; legacy flat histories are migrated on load.
- **A/B studio**: An assistant turn's fork action, pointed at `eval_stories/` instead of `stories/`, captures that turn. Studio mode then regenerates it under two **arms** at once — each arm a model plus an instruction version, `n` lanes per arm, all concurrent background tasks (SocketIO threading mode gives each provider's blocking request its own thread), each streaming into its own column. Lanes are fully independent: separate provider, separate copy of the story context, no narrator involvement, no writes to any story. When caching is on and `n > 1`, one **primer** lane per arm runs first and the rest wait on a `threading.Event` until it starts producing output, so they read the shared prefix from cache instead of each paying to write it. Finished runs are saved under `runs/` and can be replayed from the dropdown.
- **History archiving**: Distinct from branching. The whole conversation can be archived to `previous/{n}.json` (e.g. after summarization) and a fresh tree started, with archived history displayed above a separator.
- **No tests or CI** exist currently.
- **No default browser dialogs** — Never use `alert()`, `confirm()`, or `prompt()`. Always use custom-styled popups/modals.
- **UI polish conventions** (all in `styles.css`):
    - **Default visual direction — square, compact, hairline-separated** (the shared `.side-popup` / `.modal-overlay` rules are the reference implementation). It covers the chrome: popups, modals, both sidebars, menus, and the studio. Rendered content keeps its own look — narration blocks, markdown `pre`/`code`, and the chat-area buttons/pills are deliberately still rounded. New or reworked UI gets: `border-radius: 0` on the surface and everything in it (inputs, selects, dropdowns, checkmarks, buttons); tight padding (~7–10px on headers/bodies/footers, ~5px on controls, ~4px between a caption and its control); 1px `var(--border)` hairlines as the separator — between grouped rows, under headers, above footers — instead of nested boxes or fills; section captions as small uppercase letterspaced `var(--text-muted)` text (`0.68rem`, `font-weight: 600`, `letter-spacing: 0.07em`); row hover is a background highlight (`var(--bg-alt)` on popup surfaces, `var(--sidebar-active)` in the sidebars) plus a text-color lift to `var(--text-bright)`.
    - Never `transition: all` — list the exact properties that change (e.g. `transition: color, background-color`). `all` forces the browser to watch everything and animates props you didn't intend.
    - Where an older component still uses rounded surfaces, keep nested radii concentric: outer radius = inner radius + padding between them.
    - `font-variant-numeric: tabular-nums` on any live-updating numbers (costs, branch counters) to stop width jitter.
    - Buttons get `transform: scale(0.96)` on `:active` (never below `0.95`).
    - `text-wrap: balance` on headings, `text-wrap: pretty` on short UI text; leave long book-narration prose on default.
